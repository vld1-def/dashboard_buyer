# check-domains

Перевіряє домени з сервера й пише результат назад у таблицю `domains`.

## Навіщо окрема функція

Дашборд — статична сторінка. Код відповіді чужого домена вона прочитати
не може: CORS блокує читання, а режим `no-cors` повертає статус `0` і
для `200`, і для `404`. Тобто з браузера видно рівно одне — відповів
домен чи ні.

Тут запит іде з сервера, де CORS не існує. Звідси справжній код
відповіді, і звідси ж можливість спитати Google про чорний список.

## Розгортання

Через браузер: Supabase Dashboard → Edge Functions → Deploy a new
function → редактор → вставити `index.ts` → Deploy.

Або з термінала, з папки репозиторію:

```bash
supabase functions deploy check-domains
```

## ⚠️ Після розгортання: вимкнути перевірку JWT

**Edge Functions → check-domains → Settings → JWT Verification → Disable.**

Без цього кнопка Deep check падає з `Failed to fetch`, і причина не
очевидна. Перед POST браузер шле запит OPTIONS — питає дозволу на
міждоменний виклик. Заголовка `Authorization` у цьому запиті немає
**ніколи**: так влаштовані браузери. Якщо перевірка JWT увімкнена, шлюз
Supabase відкидає цей OPTIONS з 401 ще до того, як почне працювати код
функції, — і браузер каже лише «Failed to fetch», без жодних деталей.

Вимкнути її тут безпечно, і ось чому:

- функція сама вимагає заголовок `Authorization` і без нього повертає 401;
- клієнт Supabase створюється з токеном того, хто викликав, тож RLS
  лишається в силі — чужих доменів вона не побачить;
- ключ сервісної ролі не використовується взагалі.

Тобто «вимкнено» стосується лише шлюзу. Перевірку робить сама функція,
просто після того, як відповість на OPTIONS.

### Якщо не допомогло

Перевірте з термінала — `curl` не робить preflight, тож CORS не заважає:

```bash
curl -i -X POST \
  'https://ВАШ-ПРОЄКТ.supabase.co/functions/v1/check-domains' \
  -H 'Content-Type: application/json' -d '{}'
```

| Відповідь | Що означає |
|---|---|
| `{"error":"no authorization header"}` | функція жива, справа була в CORS |
| `{"code":401,...}` від шлюза | перевірка JWT усе ще ввімкнена |
| 404 | функція не розгорнута або названа інакше |

## Чорний список Google: який саме API

Два різні продукти на тій самій базі даних.

| | Web Risk | Safe Browsing v4 |
|---|---|---|
| Для чого | комерційне використання | **тільки некомерційне** |
| Ціна | безкоштовний обсяг + оплата за перевищення | безкоштовно |
| Запит | один GET на домен | пакетно, до 500 URL |
| Змінна | `WEB_RISK_KEY` | `SAFE_BROWSING_KEY` |

Умови Safe Browsing прямо забороняють використання «for sale or
revenue-generating purposes». Якщо дашборд обслуговує бізнес — потрібен
Web Risk.

Функція бере `WEB_RISK_KEY`, якщо він є; інакше `SAFE_BROWSING_KEY`;
без жодного працює, просто не ставить `danger`.

```bash
supabase secrets set WEB_RISK_KEY=AIza...
```

Або в браузері: Project Settings → Edge Functions → Secrets.

### Де взяти ключ

1. `console.cloud.google.com` → створити або вибрати проєкт
2. APIs & Services → Library → знайти **Web Risk API** → Enable
3. APIs & Services → Credentials → Create credentials → API key
4. Обмежити ключ цим одним API (Restrict key → Web Risk API)

Для Web Risk у проєкті має бути привʼязаний білінг, навіть щоб лишатись
у межах безкоштовного обсягу.

## Про схему в URL

Надсилаємо лише `http://домен/`. Схема ролі не грає: під час канонізації
Google відкидає схему, логін, пароль і порт — збіг шукається за хостом і
шляхом. Тому `https` окремо питати не треба.

## Порціями

За один виклик перевіряється до 200 доменів — Edge Function обмежена в
часі. У відповіді є `more` і `next`; дашборд ходить по колу з курсором
`after`, поки `more` не стане `false`.

## Статуси

| Код | Статус | Що означає |
|---|---|---|
| 2xx, 3xx | `ok` | відповідає |
| 404 та інші 4xx | `notfound` | домен живий, але сторінку не віддає |
| 5xx | `down` | сервер відповідає помилкою |
| немає відповіді | `down` | DNS, сертифікат, відкинуте зʼєднання, таймаут |
| — | `danger` | у чорному списку Google |

`danger` перекриває код відповіді: домен у списку віддає звичайні `200`,
і саме тому сам ти його не помітиш.

`HEAD` пробується першим; якщо сервер відповідає `405` або `501` —
повторюємо `GET`, бо це не діагноз домена, а невміння сервера.

## Безпека

Функція працює від імені того, хто її викликав: клієнт Supabase
створюється з його токеном, тож RLS лишається в силі й чужих доменів
вона не бачить. Ключ сервісної ролі свідомо не використовується.
