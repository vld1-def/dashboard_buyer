# fb-sync

Щогодини питає Marketing API про кабінети й складає відповідь у
`fb_accounts`.

## Що саме забирає

| Що | Звідки | Нащо |
|---|---|---|
| стан кабінета | `account_status`, `disable_reason` | головне: забанений кабінет має бути видно одразу, а не за три дні |
| витрати сьогодні | `insights` за `date_preset=today` | скільки вже відкручено, поки день іде |
| кампанії / адсети / оголошення | `summary=total_count`, окремо всі й окремо `effective_status=ACTIVE` | скільки всередині живого |
| картка | `funding_source_details.display_string` | чим платить, щоб відрізнити кабінети в парку |

### Біна картки немає й не буде

Marketing API не віддає перших шести цифр — ніде, жодним полем. Це дані
платіжної системи, і Facebook їх не публікує. Максимум, що є, це рядок
виду `Visa *4242`: тип і останні чотири. Воно й лежить у полі `card`.
Шукати бін в інших полях не варто, його там немає.

## Що НЕ робить

Не чіпає `accounts_mapping`. Там статус ставить людина, часто всупереч
Facebook («живий, але ми його відклали»), і імпорт, який щогодини
затирав би чужу позначку, був би не помічником, а джерелом сюрпризів.
Машинне й ручне лежать у різних таблицях і не б'ються.

Змінився стан кабінета — пише рядок у `account_events`, тобто в ту саму
стрічку «що сталося», яку дашборд уже показує на сторінці Cabinets.
Першого прогону не пише нічого: порівнювати ще нема з чим, і вивалювати
весь парк одним махом було б рівно тим шумом, від якого ми тікаємо.

## Два входи

**Зі сторінки** — кнопка «Sync now» у Налаштуваннях. Заголовок
`Authorization` несе токен людини; функція питає Supabase Auth, хто це,
і бере **тільки її** токени. Ключ сервісної ролі тут потрібен — інакше
не прочитати `fb_tokens.token`, він закритий навіть від власника, — але
межі ставить перевірений uid, а не те, що попросили в тілі запиту.

**З розкладу** — заголовок `x-cron-key` зі спільним секретом
(`CRON_SECRET`, той самий, що й у нічної перевірки доменів). Тоді
обходить усіх.

Тіло запиту може містити `{"token_id": 3}` — синхронізувати лише один
токен.

## Відповідь

```json
{"cron":true,"tokens":2,"accounts":37,"failed":0,"changed":3,
 "throttled":false,"more":false,"problems":[]}
```

`throttled: true` означає, що вперлись у ліміт Facebook і вийшли самі.
Це не помилка: ліміт рахує навіть відмовлені запити, тож довбати далі —
найгірше з можливого. Решта добереться наступною годиною.

## Розгортання

```bash
supabase functions deploy fb-sync
```

Деплойте **з кореня проєкту**, щоб CLI підхопив `supabase/config.toml`:
там для цієї функції вимкнена перевірка JWT шлюзом. Вона заважає двічі —
розклад ходить без токена людини, а браузер перед POST шле preflight
`OPTIONS`, який за стандартом іде без `Authorization` завжди. Деплоїте
інакше — додайте флаг явно:

```bash
supabase functions deploy fb-sync --no-verify-jwt
```

Функція від цього не стає відкритою: без заголовків вона відповідає 401.

## Секрети

| Ім'я | Обов'язковий | Що це |
|---|---|---|
| `SUPABASE_URL` | так | Supabase кладе сам |
| `SUPABASE_ANON_KEY` | так | Supabase кладе сам |
| `SUPABASE_SERVICE_ROLE_KEY` | так | Supabase кладе сам. Якщо у вашому проєкті його немає — додайте `SERVICE_ROLE_KEY` руками |
| `CRON_SECRET` | лише для розкладу | спільний секрет, той самий, що й у `check-domains` |
